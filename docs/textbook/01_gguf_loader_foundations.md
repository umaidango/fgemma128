# 教材 第1章: バイナリを読む — GGUFローダの基礎（M0前半）

この章のゴール: **GGUFファイルのヘッダとメタデータとテンソル情報を、自分のCコードで読み出せるようになること。**
ここまでできれば M0 の半分が終わる。残り半分（テンソル形状表の確定）は演習4の成果物そのもの。

進め方の約束（CLAUDE.md準拠）:

- 詰まったら AI に聞く。ただしヒントは レベル1（指摘）→ レベル2（概念）→ レベル3（方針） の順でしか出てこない。それで正しい。
- 各演習の最後に「分かったことを自分の言葉で3行」書いてから次へ進む。

## 準備

1. 対象ファイルを入手する: 公式QAT版 `google/gemma-4-E2B-it-qat-q4_0-gguf`（約3.35GB）。
   - 置き場所はリポジトリの外か `models/` の中。**リポジトリにコミットしない**（.gitignore済み）。
2. 照合用の道具を確認する: `xxd`（先頭バイトの目視）、Python（自分で書く照合スクリプト用）。
3. 実ファイルの先頭をまず目で見る（演習1でやる）。

## 概念1: ファイルはバイト列であり、オフセットで考える

- 3.35GBのファイルを `fread` で丸ごと読む設計と、`mmap` で必要なページだけ触る設計の違いを考える。GGUFは最初から mmap される前提で設計されている（テンソルデータが整列されて並んでいるのはそのため）。
- 以後のパースは「カーソル（現在位置）を進めながら読む」一つの流れになる。すべての読みは「いま何バイト目にいて、次に何バイト読むか」で説明できるはず。

## 概念2: 固定幅整数とエンディアン

- `int` のサイズは環境依存。バイナリ形式を読む時は `stdint.h` の `uint32_t` / `uint64_t` 等で読む。
- GGUFはリトルエンディアン。x86-64 / ARM64（通常モード）はどちらもリトルエンディアンなので、まずは「生のバイト列をそのまま整数として読める」前提で進めてよい。ただし、なぜそれで正しいのかは説明できること（チェックポイントに出す）。

## 概念3: 構造体へ一括で読み込む罠

- Cの構造体にはパディング（隙間）が入る。ファイル上の並びと構造体のメモリ上の並びは、一般には一致しない。
- だからこのプロジェクトでは「構造体に `fread` で一発読み」はせず、**フィールドごとにカーソルから読む**方式を採る。地味だが、移植性とデバッグのしやすさで勝る。
- 文字列について: GGUFの文字列は「u64の長さ + そのバイト数」が並ぶ形式で、**末尾の `\0` はない**。C文字列として使うには自分で終端処理が要る。ここを忘れると静かに壊れる。

## 概念4: GGUFの地図（v3）

ファイルは4つの区画からなる。

| 区画 | 内容 |
|---|---|
| ヘッダ（24バイト固定） | magic `GGUF`（4バイト）、version（u32、現行3）、tensor_count（u64）、metadata_kv_count（u64） |
| メタデータ | KVの繰り返し。各KVは「キー文字列、値の型（u32のenum）、型に応じた値」。値の型には整数/浮動小数/bool/文字列/配列がある。配列は「要素型 + u64の要素数 + 要素の並び」 |
| テンソル情報 | 各テンソルについて「名前文字列、次元数（u32）、各次元の大きさ（u64×次元数）、型（u32）、オフセット（u64）」 |
| テンソルデータ | テンソル情報の直後からではなく、**alignment（既定32、`general.alignment` で変更可）の境界まで切り上げた位置**から始まる。各テンソルのオフセットはこの区画の先頭からの相対値 |

覚えるべきポイント:

- データ区画の開始位置の計算を間違えると、全テンソルが少しずつずれて読める。「少しずれる」は「全然読めない」より発見が遅れるのでたちが悪い。
- メタデータのキー例: `general.architecture`（値は `gemma4` のはず）、`gemma4.context_length`、`gemma4.block_count`、`gemma4.attention.sliding_window`、`gemma4.embedding_length_per_layer_input`、`tokenizer.ggml.tokens`（巨大な配列）。

## 概念5: ggmlの次元順は「逆」

- GGUFのテンソル次元は ggml の `ne` の順で記録され、**ne[0] が最も速く変化する軸**。NumPy/HFの形状表記とは逆順になる。
- 例: HFで `[out, in]` と書かれる行列が、GGUFでは次元 `[in, out]` の順で出てくる。
- 形状表を作る時は、どちらの表記で書いたかを必ず明記する。ここでの読み違いは M1 以降すべての計算を壊す。

## 概念6: テンソルのバイトサイズを計算する

オフセットとファイルサイズの検証には、各型の「要素数→バイト数」変換が必要。

| 型 | ブロック | バイト数 | 備考 |
|---|---|---|---|
| F32 | 1要素 | 4 | norm系はほぼこれ |
| F16 | 1要素 | 2 | |
| Q8_0 | 32要素 | 34（fp16 scale + 8bit×32） | 参照用の単純な量子化 |
| Q4_0 | 32要素 | 18（fp16 scale + 4bit×32） | 値 = d × (q − 8)。本命ファイルの主形式 |
| Q4_K | 256要素（スーパーブロック） | 144 | scale/min の詰め込みが複雑。今回はサイズ計算だけできればよい |

## 演習

### 演習1（目視）: 先頭を覗く

- `xxd` で実ファイルの先頭128バイトを表示し、magic と version と、2つのカウントらしき値を手で読む。
- 自分の読みが合っているか、概念4の表と突き合わせる。ここで読んだ値をノートに残す（後の演習の照合に使う）。

### 演習2（コード）: ヘッダを読む

- ファイル名を引数で受け取り、ヘッダを **フィールドごとに** 読んで、magic / version / tensor_count / metadata_kv_count を表示するプログラムを書く。
- 合格条件: magic が `GGUF` でなければエラーで終了する。version は 3。2つのカウントが演習1の目視と一致し、どちらも「ありえない値」（例: 10億）になっていない。

### 演習3（コード）: メタデータを列挙する

- 全KVを走査し、キーと値の型を一覧表示する。スカラーと文字列の値は中身も表示する。
- 配列型は中身を追わず「要素型と要素数」だけ表示してスキップする（トークナイザの配列は巨大なので、まずはそれで正しい）。
- 合格条件: `gemma4.*` の主要キーが読め、context_length = 131072、block_count = 35 が自分のプログラムの出力で確認できる。

### 演習4（コード＋成果物）: テンソル情報をダンプし、形状表を確定する

- 全テンソルの「名前、次元（ggml順とHF順の両表記）、型、オフセット」をダンプする。
- 検証を入れる: 最後のテンソルの終端（オフセット + バイトサイズ）がファイルサイズと一致するか（概念6の計算を使う）。
- このダンプから、次の3点を自分の目で確定して `docs/notes/m0_tensor_shapes.md` に記録する。これが調査メモの未確定事項を潰す成果物になる:
  1. **double-wide MLP**: 層ごとに ffn_gate の次元を比べ、どの層から幅が変わるか（変わらないか）。
  2. **共有層の欠落**: 15〜34層に attn_k / attn_v / attn_k_norm が無いこと。
  3. **PLE系**: per_layer_token_embd の形状と型。あわせて AltUp 系テンソルの有無。
