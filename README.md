# fgemma128

**Fast Gemma 4 E2B on CPU, with a real 128K context — hand-written C.**

CPUで Gemma 4 E2B を動かすための推論エンジン。C言語。最大の目標は、スペック表の数字ではなく **実際に使える128Kコンテキスト** を、普通のCPUマシンで成立させること。

- 対象モデル: `google/gemma-4-E2B-it`（テキストのみ。vision / audio は対象外）
- モデル形式: **GGUF**（safetensorsは使わない。重み・メタデータ・トークナイザが1ファイルに入っている）
- 最初の対応ファイル: 公式QAT版 `google/gemma-4-E2B-it-qat-q4_0-gguf`（Q4_0はブロック構造が最も単純で、最初の実装に適している）。正しさの参照用にQ8_0、後段でQ4_K_M（Unsloth版等）へ広げる
- 言語: C（C99以降を想定、依存は最小限に）
- ライセンス: MIT（[LICENSE](LICENSE)）
- 技術的な根拠と数値: [docs/RESEARCH_MEMO.md](docs/RESEARCH_MEMO.md)（アーキテクチャ実値、KV計算、勝ち筋の分析）

## なぜ作るのか（二つの目的）

1. **技術として**: Gemma 4 E2B は MQA（KVヘッド1）・層間KV共有・sliding window のおかげで、正しく実装すれば128K時のKVキャッシュは fp16 でも約774MiBしかない。一方で prefill は128Kで約850 TFLOP級あり、現実の体験を決めるのは「再計算を避ける設計」と「長文脈での帯域の使い方」になる。ここにはまだ設計の余地がある。
2. **人として**: これはプログラミング技能を取り戻すためのプロジェクトでもある。だからコードは人間が手で書く（次の「鉄のルール」参照）。速く作ることより、理解して書くことが目的の一つ。

## 鉄のルール: AIはコードを書かない

> **このリポジトリのコードは、すべて人間が書き、すべての行をその人間が説明できなければならない。**

- AI（Claude、ChatGPT、Copilot、その他すべての生成AI・コーディングエージェント）に、実装コードを書かせてはいけない。補完で出てきたコードをそのまま使うのも同じこととする。
- AIの役割は **アシスタントと教材係だけ**：概念の説明、設計の壁打ち、人間が書いたコードのレビュー（指摘まで。修正コードは書かない）、教材・演習問題の作成、ベンチマーク結果の分析。
- これは協力者全員に適用される。詳しくは [CONTRIBUTING.md](CONTRIBUTING.md)。
- AI向けの指示書は [CLAUDE.md](CLAUDE.md)。AIにこのリポジトリで作業させる前に、必ず読ませること。

正直に言うと無駄な使い方だし、面倒なルールだと思う。それでもこのプロジェクトでは、それが本体だ。コードを書く能力そのものを取り戻すのが目的なら、近道は目的の裏切りになる。

## 先行プロジェクトとの違い

- **llama.cpp**: 最強の汎用実装。本プロジェクトのベンチマーク基準。汎用性では勝負しない。「E2B専用・128K運用専用」に絞ることで差を作る。
- **gemma4.c**（Ryan Senn）: 約700行の純CでE2B推論を実装した教育用プロジェクトで、短文脈では既に速い。本プロジェクトは「純Cで動く」こと自体を新規性とは主張しない。違いは **128Kの実運用**（正しいKV、prefill再計算の回避、長文脈decode）に全振りする点。
- **kimi-k3-in-c**: 着想源。MoEの疎さを使う手法は dense な E2B には使えないが、「疎なものは常駐させない」「全条件で出力一致を検証する」「ベンチの前提を正直に書く」という姿勢は借りる。

## ロードマップ

| 段階 | 内容 | 合格条件 |
|---|---|---|
| M0 | GGUFローダ（ヘッダ/メタデータ/テンソル情報）+ テンソルダンプ | 層別の形状表が確定する（特に double-wide MLP の適用範囲と、共有層に attn_k/v が無いことの確認） |
| M1 | スカラー版 forward（1トークン、Q4_0/Q8_0の逆量子化込み） | llama.cpp（同じGGUF） と top-1 トークン一致、hidden の cosine ≒ 1.0 |
| M2 | KVキャッシュ（層間共有 + sliding window）で複数トークン生成 | 1K文脈で参照実装と一致 |
| M3 | Q4_K 対応 + GEMV最適化（SIMD）+ スレッド化 | 短文脈で llama.cpp と同等以上 |
| M4 | 長文脈: チャンク prefill、KV量子化、state 保存/再開 | needle テスト 32K / 128K 合格、再開が再計算より桁で速い |
| M5 | PLE ストリーミング、RSS仕上げ、ベンチとREADME整備 | 公開可能な再現性（誰が回しても同じ数字と出力） |

進め方と判定基準（どこで「勝った」と言い、どこで見切るか）は調査メモ §11 に書いた。スター数は需要とみなさない。
